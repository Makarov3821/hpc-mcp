# 常用提交脚本分析

分析日期：2026-10-08。对象：`qg16`、`qrest`、`qvasp`。

本次完成源码审查及 Python 3 AST 语法解析，没有执行、导入这些程序，也没有访问集群或修改原脚本。软件路径、调度资源语义和实际生成脚本的运行行为仍需远程验证。本文记录兼容需求，不表示这些功能已经实现。

## 1. 总体结论

三个文件都是 Python 编写的应用专用提交工具：解析命令行、生成调度脚本，再调用调度器。仅分析 Shell 指令无法保留其完整行为。

需要三层适配：调度器适配（LSF/Slurm）、应用配置（Gaussian/REST/VASP）、入口流程（扫描、筛选、输入修改、打包、提交）。新增应用优先通过模板与规则扩展；复杂流程采用明确的兼容适配器，不承诺解释任意 Python 程序。

## 2. 脚本能力对照

| 项目 | qg16 | qrest | qvasp |
| --- | --- | --- | --- |
| 应用 | Gaussian 16 | REST SIF 镜像 | VASP |
| 调度器 | LSF | LSF/Slurm/Torque 分支，当前 LSF | LSF |
| 输入发现 | 单个 `.gjf` 或目录，可递归 | 当前 `ctrl.in` 或递归扫描 | 当前目录运行，未检查输入集合 |
| 并行 | 单计算多核，或多计算跨节点打包 | OpenMP 或 MPI | MPI，另有 OpenMP 二进制选项 |
| 输入修改 | `%nproc*`、`%mem` | `num_threads` | 无 |
| 仅生成 | `-P`，仍可能修改输入、查询队列 | `-P`，仍修改输入、检查镜像 | `-d`，写 `vasp.lsf` 后展示 |
| 提交编号 | 标准输出被丢弃 | 不解析，可能被抑制 | 写入 `<jobid>.jobid` |
| 结果线索 | 同名 `.log`、调度 `.out`、输入中指定的文件 | `rest.log`、调度 `.out` | `log.out`、调度 `.out`，其他结果待定义 |

## 3. qg16：Gaussian 扫描与多任务打包

### 确定行为

- 默认 `Gaussian` 队列、28 核、AVX2 版本；版本到安装路径的映射在文件头部。
- 扫描 `.gjf`，可检查日志末尾 2048 字节中的 `Normal termination of Gaussian 16`，并尝试通过 `bjobs` 的工作目录和命令识别活跃输入。
- 目录模式且队列属于 `xppn1/xppn2/xppn3` 时自动打包。默认每组 4 个，允许 4–32 个，不是调度器数组。
- 单计算修改核数；内存优先级为 `--mem`、输入已有值、100GB 回退。
- 打包强制每个计算使用 28 核和 180GB；按指定组大小申请核数，末组不足时仍申请整组资源。
- 通过 `$LSB_HOSTS` 去重得到主机列表，用 `blaunch` 在各节点启动计算；多个计算共享一个 LSF 作业编号。
- 默认 scratch 为 `/scratch/scr/$USER/...`，生成脚本包含清理逻辑。`local-scratch` 与 `keep-scratch` 虽有生成器代码，CLI 已注释，不属于当前可用选项。

### 兼容重点与问题

- 数据模型必须有独立计算任务 `task`：一个调度器 `run` 可关联多个 task，各有输入、日志、结果和应用完成状态。
- 调度脚本有清理、`echo`，打包脚本以 `wait` 和 `echo` 收尾，未显式汇总每个计算的失败码。调度器完成不代表全部 Gaussian 计算成功。
- `submit_job` 使用 `stdout=DEVNULL` 丢弃作业编号，提交后默认删除脚本；MCP 必须自行捕获编号、保留最终快照。
- 单计算虽计算了 `mem_limit_mb`，实际生成的 LSF 内存指令全部注释，不能把 Gaussian `%mem` 当成已向调度器申请的内存。
- 打包的 `rusage[mem=...]` 和 `-M` 需要依据站点的内存单位及资源作用范围验证，不沿用注释中的每节点推断。
- 无单位内存的换算实现比注释中的 MB 换算多乘了 1024；迁移时需建立单位测试，避免复制该逻辑。
- 队列查询失败返回空集合，现有工具不能区分“无活跃任务”和“查询失败”。MCP 要返回未知／失败，不能据此放心重复提交。
- 路径展开使用运行机器的 HOME 和环境；MCP 在本地读取远程路径时必须区分两端命名空间。
- 多层 `blaunch` 引号与变量展开须用生成样本和 Shell 语法检查验证。Python 3 AST 解析还发现第 530 行无效转义警告。

主要源码位置：配置 9–36 行；完成与活跃检测 39–183 行；输入修改 241–350 行；单作业生成 352–438 行；打包生成 440–554 行；提交 556–591 行；筛选及执行 663–888 行。

## 4. qrest：镜像版本、线程与递归提交

### 确定行为

- 文件头配置调度器、镜像目录、默认版本和 Intel MPI 初始化命令；当前调度器是 LSF。
- 直接执行远程 `.sif` 文件；MPI 模式通过 `mpirun -np` 启动。实际镜像运行时兼容性需集群验证。
- OpenMP 将环境线程数和 `ctrl.in` 的 `num_threads` 设为指定数量；MPI 将二者设为 1，并启动指定数量的进程。
- 递归搜索 `ctrl.in`，以所在目录名命名，每个目录分别提交。
- 生成脚本包含绝对 `cd` 路径、`RUNNING` 文件和退出时移除标记的 trap；标记文件并非可靠的调度状态来源。

### 兼容重点与问题

- 默认队列 `single`，配置键是 `Single`；`get_queue_config` 未知队列返回 `(1, 4)[1:3]`，即单元素元组，LSF 分支解包两个变量会失败。
- `get_default_procs` 没有被实际调用，不能按照帮助或队列表推断默认进程数会自动调整。
- Slurm 分支固定生成 `-n procs`；OpenMP 模式需明确“一任务、多 CPU”的资源模型，不能只继承 MPI 式参数。当前 Slurm 分支也未生成内存请求。
- `subprocess.run` 未检查非零返回码；递归成功计数无条件增加，因此输出中的“成功处理”不是提交成功证据。
- `-P` 仍会修改 `ctrl.in`，也要求所选镜像存在；本地无远程镜像时不能直接运行原入口生成脚本。
- 输入修改使用字符串查找和替换，缺少配置语法验证；迁移应在工作副本上修改，展示差异。
- 输入引用的其他数据与 REST 结果清单不能仅凭入口确定，需要代表性 `ctrl.in` 和输出样本。
- Torque 为已有代码分支，当前产品范围仍只承诺 LSF/Slurm。

主要源码位置：配置 9–21 行；队列表 45–52 行；参数与镜像验证 112–182 行；输入修改 203–224 行；命令与脚本生成 226–288 行；提交 290–340 行；递归 342–408 行。

## 5. qvasp：站点二进制选择与 MPI 提交

### 确定行为

- shebang 指向站点 Anaconda2 Python；源码可被当前 Python 3 AST 解析，但不代表运行环境已验证。
- 默认 4 节点、每节点 28 核，申请总核数为两者乘积；`span[ptile=...]` 表达布局要求。
- 根据 VASP 版本、`std/gam/ncl`、队列、OPTCELL、OpenMP、HDF5 拼接二进制名。
- 初始化 Intel MPI 环境，链接远程 `vdw_kernel` 文件，使用 `mpirun -bootstrap lsf`，重定向到 `log.out`。
- 固定写 `vasp.lsf`，解析 `bsub` 文本并保存编号文件。

### 兼容重点与问题

- 计算目录必须相互隔离，避免固定脚本名和 `log.out` 相互覆盖。
- 二进制版本和硬件后缀是站点配置，不应泛化成所有集群通用规则；需要远程检查所选可执行文件。
- OpenMP 选项只改变二进制名，没有设置线程数；混合 MPI/OpenMP 配置需另行明确。
- 没有检查 VASP 输入文件、内存、时间限制，也没有定义完整结果集合。`INCAR/POSCAR/POTCAR/KPOINTS` 等候选项及重启文件规则须结合用户实际流程确认。
- Shell 命令拼接未引用路径，`os.system` 的返回值未校验，作业编号依赖固定输出格式；MCP 应接管提交与错误处理。
- 内核数据来自远程软件目录，应该作为远程依赖，不上传本地副本或自动跟随链接复制。

主要源码位置：生成与二进制选择 23–71 行；参数 75–138 行；资源检查及提交 139–166 行。

## 6. 推荐接入方式

1. **静态分析**：Python AST 提取参数定义、常量、模板字符串和副作用位置，结合人工／模型解释生成配置；不执行源码以解析参数。
2. **受控兼容生成**：对这三个已分析工具提供明确适配，在隔离工作副本中准备输入与生成调度脚本。原 `-P/-d` 仅作为参考能力，不直接视为无副作用 dry-run。
3. **MCP 接管提交**：生成脚本交统一调度适配器执行，捕获所有编号和原始响应，历史记录与文件同步不依赖原工具打印。
4. **逐步模板化**：把站点软件路径、资源策略和应用输入规则拆为配置，保留原脚本版本和实际生成结果用于比对。

首轮建议先做 qg16 单计算闭环，随后 qrest 的 LSF/Slurm 单目录，接入 qvasp 的单目录配置；批量扫描和 qg16 packing 在 task/run 模型及失败检测就绪后加入。

## 7. 计划补充与验收样本

- 增加 Python 入口分析，保留 Shell 分析用于生成脚本；明确通用静态分析与特定入口适配的边界。
- 预览只读，输入变更在执行工作副本中进行，记录原始和有效输入校验值、差异。
- 分离调度器状态与应用结果：Gaussian 使用终止标记作为证据；REST/VASP 判据待真实输出样本确定。
- 记录逐计算任务状态，支持 packed 作业的部分失败、结果同步及选择性重跑。
- 测试默认及未知队列、OpenMP/MPI、带空格路径、末组不足、输入修改、编号捕获、排队查询失败和应用失败被收尾命令掩盖。
- 仍需代表性 `.gjf`（含 checkpoint/重启引用）、`ctrl.in`、VASP 输入目录，以及完成／失败输出样本。仅靠三个提交器不能确定全部文件依赖和科学计算成功判据。
